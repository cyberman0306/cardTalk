# 카드톡 사용성 진단과 질문 개정안

2026년 11월 20일 · Windows 2025HOMEPC · `feature` / `6f2fa45` · 한국어로 진행하는 2~6인 독서·취미 모임을 기준으로 평가했다.

**진단 뒤 반영한 변경**

홈에서 실제 질문을 먼저 읽고, 휴대폰을 건네는 삽화와 덱별 색·무늬로 진행 방식을 볼 수 있게 했다. 320×568에서는 기본 4명·두 바퀴의 ‘총 8차례 시작’ 버튼 하단이 736px에서 506px로 올라왔다. 앞면에는 답하지 않고 건네는 안내를 넣었고, 교체 카드를 다 쓴 마지막 자리에는 대화를 마칠 수 있다는 문구가 나온다. 질문 표에서 ‘먼저 낭독’으로 표시한 8장은 본질문이나 꼬리 질문을 개정해 같은 카드 ID로 반영했다. 아래 진단 수치와 원문은 기준 커밋 시점의 기록이다. [개선한 홈](usability-evidence/home-after-cover.png) · [개선한 320×568 준비 화면](usability-evidence/setup-after-320.png)

**첫 모임에서 한 바퀴를 진행하는 용도로는 잘 맞는다. 다음 개선은 참가자가 대답하고 싶지 않은 순간에 집중할 만하다.** 기본 설정에서는 덱 선택, 시작, 뒤집기 세 번으로 첫 질문에 도달한다. 질문을 교체해도 자기 자리가 유지되고, 앱을 닫았다 열어도 이어 할 수 있다. 하지만 평소 카드 앞면에서 읽을 수 있는 말은 ‘질문 바꾸기’와 ‘다음 차례’다. 낯선 사람 앞에서 “이건 대답하지 않아도 되나요?”라고 확인하는 부담을 화면이 충분히 덜어 주는지는 실제 모임에서 검증해야 한다.

| 순서 | 먼저 할 일 | 성공했다고 판단할 장면 |
| --- | --- | --- |
| 1 | 카드 앞면에서 답변을 건너뛸 수 있다는 점과 두 버튼의 차이를 알린다. | 처음 폰을 받은 사람이 도움 없이 자기 자리에서 질문을 바꾸거나, 답 없이 다음 사람에게 건넨다. |
| 2 | 준비 화면을 줄이고 한 대로 하는 게임임을 홈에서 알린다. | 작은 폰에서도 주최자가 인원과 총차례를 확인하고 첫 카드를 연다. |
| 3 | 먼저 낭독할 8장의 본질문과 꼬리 질문을 비교한다. | “없어요” 같은 짧은 답을 존중하고, 대화를 이어갈 때는 방금 들은 말에 연결한다. |
| 4 | 같은 덱을 다시 꺼낼 때 이미 본 질문의 순서를 조정하는 안을 시험한다. | 두 번째 모임에서 실제로 새 질문을 만나는 시점이 빨라진다. |

## 한 판을 돌려 본 결과

| 상황 | 직접 확인한 동작 | 판단과 제안 |
| --- | --- | --- |
| 홈에서 덱 고르기 | 390×844에서 추천 덱 시작 버튼과 네 덱의 표지가 보인다. 1280×800에서는 네 덱이 한 줄이다. 홈 본문에 한 대로 하는 방법과 인원은 없고 준비 화면에서 나온다. | 종이 카드 사진과 덱별 색·무늬는 실제 앞뒷면과 이어져 선택한 덱을 알아보기 쉽다. 추천 영역의 설명 한 줄을 “2~6명이 휴대폰 한 대를 돌려 가며 이야기해요”로 시험한다. |
| 준비와 첫 질문 | 기본은 4명·두 바퀴, 총 8차례다. 390×844에서는 시작 버튼이 y=661~709에 있다. 320×568에서는 y=688~736으로 한 번 내려야 보인다. 스크롤하면 누를 수 있다. | 작은 화면에서는 덱 이름·표지·소개를 짧게 묶어 인원·바퀴·시작을 가까이 둔다. 한 바퀴 기본값은 짧은 모임에서 비교할 가설이다. 기존 세 번의 탭만으로 시작되는 단순함은 살린다. |
| 첫 차례와 폰 건네기 | 앞면의 질문은 크게 읽히고 뒷면에 자리 번호와 인계 안내가 나온다. ‘질문 바꾸기’는 같은 자리에서 새 앞면을 보여 주고 ‘다음 차례’는 다음 자리의 뒷면으로 간다. | 앞면에는 한 줄 “답하지 않고 다음 사람에게 건네도 돼요.” 버튼 후보는 “다른 질문 보기”와 “다음 사람에게”. 마지막 자리에서는 기존 “대화 마치기”가 정확하다. 패스용 세 번째 버튼을 추가할 이유는 약하다. |
| 교체 카드를 다 쓴 경우 | 6명·두 바퀴에서 교체 여유는 총 4장이다. 네 번 바꿔도 같은 자리다. 12번째 마지막 앞면에서 ‘대화 마치기’ 아래에 “남은 카드는 다음 차례를 위해 남겨 뒀어요”가 그대로 나온다. | 마지막에는 “이 덱의 질문을 모두 봤어요. 답하지 않고 마쳐도 돼요.” 앞선 자리에서는 남은 사람들 몫을 설명한다. 두 상태를 따로 확인할 수 있다. |
| 꼬리 질문 | 버튼으로 펼치고 접을 수 있고 카드를 바꾸면 닫힌다. 320×568에서 한 예시를 펼치자 다음 차례 버튼의 하단이 y=574로 조금 내려갔다. | 자동으로 펼치지 않아도 된다. 듣는 사람이 정말 궁금한 순간에만 누를 수 있게 하고 문구를 직전 답과 연결한다. 작은 화면에서는 질문을 끝까지 읽은 뒤 바로 넘길 수 있는지 관찰한다. |
| 잠시 멈춤과 복귀 | 진행 중 새 판을 열면 확인창이 뜨고 취소하면 이어 할 수 있다. Android에서 질문을 저장한 뒤 비행기 모드로 앱을 강제 종료하고 다시 열었다. 홈의 ‘이어 하기’가 원래 질문과 책갈피 상태를 복구했다. | 끊어서 쓰는 모임에 맞는 동작이다. 도움말에 이미 있는 설명을 길게 늘리기보다 첫 사용 시 필요한 한 줄에 공간을 쓴다. |
| 책갈피와 완료 | 보관함 2장 중 1장을 해제하면 즉시 사라지고 키보드 포커스가 문서 본문으로 돌아갔다. 마지막 ‘대화 마치기’ 뒤에도 포커스가 본문에 있었다. | 보관함에는 짧은 “다시 담기”와 다음 카드 또는 빈 보관함 제목으로의 포커스 이동을 검토한다. 완료 뒤에는 완료 제목으로 포커스를 옮기는 편이 현재 위치를 다시 찾기 쉽다. [W3C 포커스 순서](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) |

작은 화면에서 시작 버튼이 어디에 놓이는지와, 참가자가 실제로 보는 카드 앞면을 비교할 수 있다. [320×568 준비 화면](usability-evidence/setup-320.png) · [390×844 카드 앞면](usability-evidence/play-390.png)

### 홈 표지에서 떠오르는 브랜드

390px 폭의 홈에서는 상단 아이콘, 추천 덱 사진, ‘처음 만난 사이’ 타일에 주황색 해 모양이 세 번 보인다. 특히 사진 속 맨 앞 카드의 길쭉한 둥근 빛살은 Claude 앱 아이콘을 연상시킨다. 카드톡의 작은 두 눈은 가까이서 보면 표정을 만들지만, 첫눈에는 주황·크림색과 바깥 윤곽이 먼저 읽힌다. 덱을 알아보게 하는 반복이 다른 브랜드까지 떠올리게 할 수 있다는 시각적 판단이다. [개선 전 홈 화면과 아이콘](usability-evidence/home-before-cover.png) · [Claude 공식 앱 아이콘](https://apps.apple.com/kr/app/claude-by-anthropic/id6473753684)

출시용 표지 후보로는 질문이 뜬 휴대폰을 테이블 건너편 사람에게 건네는 장면을 권한다. 아이콘과 첫 덱에는 두 장의 카드가 서로 포개지는 무늬를 써서 작은 크기에서도 알아볼 수 있게 한다. 첫 사용자에게는 브랜드 이름을 먼저 말하지 않고 “무엇을 하는 앱 같아요?”, “떠오르는 앱이 있나요?”를 물어 두 표지의 첫인상을 비교한다.

### 작은 글씨와 카드 모션

- 390px 폭에서 질문 저장과 도움말은 44×44 CSS px, 꼬리 질문은 높이 44px, 다음 차례와 질문 바꾸기는 48px였다. 표에서 확인한 버튼은 WCAG 2.2 AA의 24×24 CSS px 기준보다 크다. Android는 터치 영역 48×48dp를 권장한다. 특히 손을 바꾸어 쥔 직후 쓰는 책갈피·도움말·꼬리 질문의 터치 영역을 48dp 수준으로 늘리는 안을 시험할 수 있다. 좌석 숫자는 상태 표시다. [W3C 터치 영역 기준과 예외](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) · [Android 터치 영역 권장치](https://support.google.com/accessibility/android/answer/7101858?hl=en)
- Android 시스템 글꼴을 200%로 설정한 412×839 CSS px WebView에서 홈·준비·6인 카드 화면의 문서 너비는 모두 412px였다. 긴 질문과 꼬리를 펼치면 세로로 길어졌고 다음 차례 버튼은 y=974에서 시작했다. 큰 글씨를 유지하고 세로 스크롤로 조작에 도달하는 설계가 적절하다. 게임 전반의 확대·보조기기 사용성은 별도 참가자 과제다. [W3C 리플로 기준](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- 뒤집기 440ms, 교체와 인계 380ms다. 교체 중 나가는 카드는 입력과 접근성 트리에서 제외되고, 한 번 건네면 다음 사람에게 질문의 뒷면이 보인다. 웹에서 모션 감소를 켰을 때 뒤집기·교체·인계 모두 실행 중인 애니메이션 0개였고 다음 자리에 도달했다. Android 에뮬레이터에서도 동작 축소 설정 뒤 앱을 다시 열었을 때 WebView가 환경 설정을 인식했다. 카드가 무엇을 하는지 이미 구별되므로 모션 수정은 후순위다. [W3C 상호작용 애니메이션](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
- axe-core 4.14.1로 홈·준비·질문·보관함·판 교체 확인·완료의 여섯 상태에 WCAG A/AA 관련 규칙을 적용했다. 자동 확정 위반은 0건이었다. 질문 화면의 `aria-prohibited-attr`와 `color-contrast`는 도구가 수동 판정으로 남겼다. 실제 화면 읽기에서 자리와 질문이 어떤 순서로 들리는지, 보관 해제 뒤 다음 항목을 찾을 수 있는지가 다음 관찰 대상이다.

## 대화 연구에서 가져올 수 있는 판단

| 근거 | 카드톡에 적용할 판단 |
| --- | --- |
| Huang 등의 낯선 두 사람 대화 연구에서 상대가 앞서 말한 내용에 이어 묻는 행동은 상대가 느끼는 반응성과 관련됐다. 2025년 정정 공지는 일부 보고값을 바로잡고 주요 결론을 재확인했다. [원 논문](https://www.hbs.edu/ris/Publication%20Files/Huang%20et%20al%202017_6945bc5e-3b3e-4c0a-addd-254c9e603c60.pdf) · [정정 공지](https://pubmed.ncbi.nlm.nih.gov/40111841/) | 미리 쓴 꼬리 질문도 방금 나온 답에 맞아야 한다. 예를 들어 “창밖에 논이 보였으면 좋겠어요”라는 사람에게는 풍경 속에서 더 보고 싶은 것을 묻는다. 버튼을 몇 번 눌렀는지와 실제로 상대 이야기를 이어 들었는지는 별도 지표다. |
| Sprecher 등의 실험에서 처음 만난 두 사람이 번갈아 자신에 관해 이야기한 조건은 한 사람이 길게 말한 뒤 역할을 바꾼 조건보다 호감과 친밀감 등에서 좋은 결과를 보였다. [원 논문](https://www.sciencedirect.com/science/article/pii/S002210311300070X) | 현재의 자리 순환을 살릴 이유가 있다. 질문 한 장이 사람마다 달라지는 방식과 모두가 같은 질문에 한 번씩 답하는 방식 중 한국어 6인 모임에 더 맞는 쪽은 모임에서 비교해야 한다. |
| Aron 등의 친밀감 실험은 두 사람이 약 45분 동안 점차 깊어지는 과제를 수행하는 조건을 다뤘다. [원 논문](https://doi.org/10.1177/0146167297234003) | ‘한 걸음 더’의 분위기를 고르기 전에 알 수 있게 한다. 처음 보는 참가자 전원에게 깊은 질문을 자동 배정하는 데까지 일반화할 근거는 부족하다. 덱 선택 화면에서 대표 질문 한 장을 보여 주는 안을 비교할 수 있다. |
| Dwyer 등의 식사 현장 실험에서는 휴대폰을 테이블에 둔 조건에서 주의가 더 분산되고 함께하는 즐거움이 낮아졌다. 연구 대상은 일반적인 휴대폰 사용 상황이었다. [연구 논문](https://www.sciencedirect.com/science/article/pii/S0022103117301737) | 대화를 돕는 공유 폰 한 대를 쓰는 이 앱에는 별도 검증이 필요하다. 질문을 읽고 난 뒤 사람들이 폰을 내려놓는지, 대화 중 계속 조작법을 찾는지 관찰한다. |

## 국내외 제품은 같은 문제를 어떻게 푸나

스토어 설명과 제작사 사용법에 공개된 기능을 비교했다. 설치 수·리뷰 수에서 한국 모임의 선호도나 유료 전환율을 추정하지 않았다.

| 제품 | 확인한 사용 방식 | 카드톡에서 확인할 선택 |
| --- | --- | --- |

**반복 사용의 한계는 카드 수로 계산할 수 있다.** 현재 한 판 안의 순서는 중복 없는 셔플이다. 다음 판에서는 16장 전체를 다시 섞는다. 같은 덱에서 교체 없이 각각 `k`장을 보고 두 판을 독립적으로 섞으면 둘째 판에 겹치는 카드의 기댓값은 `k²/16`이다. 첫 판에서 본 각 카드가 둘째 판에 들어갈 확률이 `k/16`이기 때문이다.

| 같은 덱으로 두 판 | 판당 본 카드 | 두 번째 판에 겹치는 평균 |
| --- | ---: | ---: |
| 2명 × 한 바퀴 | 2 | 0.25장 |
| 4명 × 두 바퀴 | 8 | 4장 |
| 6명 × 두 바퀴 | 12 | 9장, 두 판 사이에 최소 8장은 겹침 |

같은 덱을 다시 시작할 때 직전에 못 본 카드를 앞에 두는 안을 먼저 시험한다. 6명·두 바퀴였다면 완전히 새 질문은 최대 네 장이다. 이 수치는 실제 재사용률과 별개다. 출시 덱이나 결제 모델을 정하기 전에 두 번째 모임에서 같은 주최자가 어떤 덱을 꺼내는지 관찰한다. [현재 셔플·차례 규칙](../src/game.ts) · [기존 시장 가설](market.md)

## 64장의 한국어 질문

본질문 64개와 꼬리 질문 64개의 문구 128개가 모두 서로 다르다. 각 쌍에 대해 처음 듣고 답의 범위가 잡히는지, 짧거나 부정적인 답도 받아들이는지, 꼬리가 직전 화제를 따라가는지, 처음 만난 사람 앞에서 개인사나 시범을 요구하는지를 읽고 판단했다.

| 덱 | 장수 | 경험이 있는지 먼저 묻는 본질문 | 먼저 낭독 | 다음 낭독 | 유지 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 처음 만난 사이 | 16 | 3 | 2 | 5 | 9 |
| 취향 수집 | 16 | 1 | 1 | 4 | 11 |
| 보통의 하루 | 16 | 6 | 3 | 4 | 9 |
| 한 걸음 더 | 16 | 9 | 2 | 5 | 9 |
| 합계 | 64 | 19 | 8 | 18 | 38 |

**19장은 ‘그런 경험·대상·일이 있어요?’에 “없어요”만으로 온전히 답할 수 있다.** “어떤 특징이 있어요?”처럼 내용을 묻는 문장은 제외한 수작업 분류다. 이런 시작은 말하고 싶지 않을 때 부담을 덜기도 한다. 편집할 지점은 그다음 문장이 경험이나 특정 답을 당연하게 받아들일 때다. ‘처음 만난 사이’와 ‘보통의 하루’의 쉬는 시간 소재처럼, 문구가 달라도 같은 이야기를 되풀이할 수 있는 쌍도 별도로 살폈다.

**먼저 낭독할 8장**은 즉석 시범, 기억·자세에 대한 전제, 화제 이탈, 뜻이 모호한 표현이 실제 답을 어떻게 바꾸는지 보기 좋다. 나머지 18장은 두 번째 비교 후보이고, 38장은 현 문구를 살린다. 아래 표에서 화살표 앞은 진단 당시 문구, 뒤는 개정안이다. 한 문장만 적힌 칸은 그대로 읽는다. 모든 제안은 카드톡을 위해 새로 쓴 문구다. [앱에 반영된 질문과 ID](../src/content/decks.ts)

## 실제 모임에서 판단할 기준

**첫 사용자 가정은 한국어로 모임을 여는 독서·취미 모임 주최자다.** 두 사람의 데이트, 6인의 첫 모임, 서로 익숙한 친구 모임은 휴대폰을 쓰는 방식이 다르다. 첫 파일럿에서는 2인과 4~6인, 첫 만남과 기존 모임을 구분해 적고 참가자 수만큼 표본을 부풀리지 않는다. [기존 시장 가설과 파일럿 기준](market.md)

| 단계 | 과제와 비교 방법 | 관찰하고 결정할 것 |
| --- | --- | --- |
| 처음 쓰기 | “네 사람이 한 번씩 말할 수 있게 시작해 주세요.” 사용법을 읽어 주지 않고 홈이 뜬 때부터 첫 본질문이 보일 때까지 잰다. 먼저 현행과 간결한 준비 화면을 소그룹에 나눠 보여 준다. | 소수 팀의 시간은 개별값과 중앙값으로 본다. 수정할 한 버전을 고른 뒤 새 10팀에서 8팀 이상이 60초 안에 첫 질문을 열고 7팀 이상이 한 바퀴를 마치는지를 본다. 두 기준은 기존 기획의 목표값이다. |
| 바꾸기와 패스 | “이 질문 대신 다른 걸 골라 답하고 싶어요”와 “이번에는 말하지 않고 옆 사람에게 넘기고 싶어요”를 다른 차례에 제시한다. 버튼 이름은 말하지 않는다. | 의도한 자리 유지 또는 이동, 잘못 누른 횟수, 진행자 도움 여부를 기록한다. 두 과제를 각각 도움 없이 마친 팀이 10팀 중 8팀 이상인지 본다. 이 수치는 이번 진단에서 제안하는 합격선이다. |
| 질문 낭독 | 우선 8장으로 원문과 개정안을 섞은 두 묶음을 만든다. 같은 팀은 같은 ID를 한 번만 듣고, 다른 팀에는 반대 문구를 준다. 수선 경험이 없는 경우처럼 짧은 답도 허용한다. | 뜻을 다시 물었는지, 본질문에서 나온 소재를 받아 꼬리를 물었는지, 이유 설명 없이 패스할 수 있었는지 센다. “그냥 넘어가고 싶었다”는 응답도 선택으로 인정한다. |
| 반복 사용 | 2주 뒤 실제로 두 번째 모임을 연 주최자에게 같은 덱을 사용했는지, 이미 본 카드가 나왔을 때 계속했는지 묻는다. | 분모는 두 번째 모임을 연 팀, 분자는 카드톡을 다시 쓴 팀이다. 다시 쓴 팀의 덱 선택과 중단 지점을 함께 본 뒤 최근 카드 순서 조정이나 추가 덱 투자를 판단한다. |

진행 기록은 팀·인원·덱·카드 ID·도움 요청·패스·차례만으로 충분하다. 사적인 답의 내용을 기록할 필요가 없다. 진행자가 방법을 가르쳐야 했던 순간과 참가자끼리 자연스럽게 이어간 순간을 구분해 적는다. 이 절차는 소규모 사용성 진단용으로, 비교 집단 간 시장 수요 차이를 추정하기에는 표본이 작다. [GOV.UK 관찰형 사용성 테스트](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)

## 검증 범위와 적용 시 주의할 점

- Windows에서 현재 소스로 웹 프로덕션 빌드와 게임 테스트 3개를 통과했다. 기존 테스트는 네 덱과 2~6명·한두 바퀴 조합에 대해 교체 중복, 남은 차례 보장, 저장 복구를 확인한다. Android 디버그 빌드는 프로젝트가 지정한 JDK 21로 성공했다. 기본 JDK 25로 시도한 Gradle 실행은 호환성 오류가 있었다. [테스트](../tests/game.test.mjs) · [빌드 환경](../README.md)
- Android API 36 에뮬레이터의 디버그 APK에 들어 있는 웹 자산 7개의 해시가 새 웹 빌드와 일치했다. 비행기 모드의 2인 한 바퀴에서는 저장·시스템 뒤로 가기·강제 종료 후 이어 하기·마지막 차례를 확인했다. 웹에서는 6인 두 바퀴 12차례와 교체 한도까지 진행했다. iOS, 실제 기기에서의 손동작과 TalkBack 낭독, 실제 모임 반응은 이번 검증 범위 밖이다.
- 개정안을 채택할 때는 책갈피와 진행 중인 판이 카드 ID를 참조한다는 점을 반영한다. 단순 교정은 ID를 유지할 수 있다. `daily-unexpected`처럼 발상이 달라지는 후보는 별도 카드로 추가할지 먼저 결정한다. 기존 ID를 제거하면 저장 카드가 걸러지거나 진행 판의 복구가 거절될 수 있다. [저장 처리](../src/storage.ts) · [진행 판 복구](../src/game.ts)
